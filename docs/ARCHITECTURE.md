# BazaarPlusPlus Architecture

This is the living architecture document for the current repository state. The code remains the source of truth; this document summarizes only behavior verified against current source paths during the 2026-07-10 documentation calibration, amended 2026-07-11 for the architecture-review batch (PRs #22–#28, #30, #31), 2026-07-13 for native game-font ownership and remote embedded data, and 2026-07-28 for the architecture-deepening batch (#161, PRs #170–#177; ADR-0011).

## Runtime Shape

BazaarPlusPlus is a BepInEx 5 plugin. `Plugin.Awake()` resolves the game build channel via `GameBuildInfoResolver`, creates `BppComposition`, installs static facades such as `BppLog`, `BppPatchHost`, localization, settings dock entries, supporters, and hotkeys, applies Harmony patches per patch class (so one broken game target degrades only its own feature, never the whole plugin), starts feature modules, builds the online and BazaarDB-link HTTP clients, then mounts Unity components onto the plugin `GameObject` (`src/BazaarPlusPlus/Plugin.cs:43-101`, `src/BazaarPlusPlus/Plugin.cs:186-197`). Teardown unmounts Unity components, disposes the composition (stopping pure features in reverse registration order), and only then destroys `CombatReplayRuntime`; this lets Run Logging settle a deferred completion while replay persistence state is still readable (`src/BazaarPlusPlus/Plugin.cs`, `src/BazaarPlusPlus/Core/Runtime/BppFeatureRegistry.cs`). Static utility teardown then releases native game-font handles, scopes, and cloned font assets through `NativeGameTypography.Reset()`.

`BppComposition` is the manual composition root; it receives the resolved `IGameBuildInfo`. It wires feature modules through `BppFeatureRegistry`, Unity components through `BppMountableRegistry`, and in-game settings rows through `SettingsDockEntryRegistry` (`src/BazaarPlusPlus/BppComposition.cs:102-162`). It also publishes the passive BazaarAgent game facades through `BazaarAgentGameBridge` so the optional host plugin can consume them without the main plugin referencing the agent core (`src/BazaarPlusPlus/BppComposition.cs:203-207`).

The main plugin project targets `netstandard2.1`, uses C# 12, publicizes game assemblies, embeds data resources, and references the three unconditional child assemblies: `BazaarPlusPlus.ModApi`, `BazaarPlusPlus.Storage`, and `BazaarPlusPlus.Localization` (`src/BazaarPlusPlus/BazaarPlusPlus.csproj:4-28`, `src/BazaarPlusPlus/BazaarPlusPlus.csproj:103-105`, `src/BazaarPlusPlus/BazaarPlusPlus.csproj:162`). Remote seed data is declared in `RemoteEmbeddedData.targets`: voice subtitles and analyzer-v4 ten-win builds share configuration-independent files under `obj/remote-data/`, use stable manifest names, download only when missing during ordinary builds, and force-refresh once for an explicit publish (`src/BazaarPlusPlus/RemoteEmbeddedData.targets:2-37`, `src/BazaarPlusPlus/RemoteEmbeddedData.targets:163-177`). The shared version is `BppVersion` in `Directory.Build.props` (`Directory.Build.props:3`).

## Game Build Channel And PTR Isolation

`GameBuildInfoResolver` classifies the running client as Online/Ptr/Unknown from the bundleVersion `-ptr` token plus a corroborating `TheBazaar.Config.ServerOption` type probe, treating disagreement as Ptr to protect the production dataset (`src/BazaarPlusPlus/GameInterop/GameBuildInfoResolver.cs:29-63`). The channel is injected into the composition (`src/BazaarPlusPlus/Plugin.cs`), stamped onto recorded runs when `RunLoggingModule` assembles the create request (`src/BazaarPlusPlus/Game/RunLogging/RunLoggingModule.cs`), and PTR runs are excluded from the upload feed (`src/BazaarPlusPlus/Game/RunLogging/Upload/RunBundleUploadStore.cs:50`, `:78`). Premise tests live in `tests/PtrCompatibility.Tests/`.

## Assemblies And Boundaries

The unconditional runtime assemblies are:

- `BazaarPlusPlus.dll`: the BepInEx plugin, Unity/game integration, feature modules, Harmony patches, embedded resources, and composition root.
- `BazaarPlusPlus.ModApi.dll`: HTTP client, routes, DTOs, and MessagePack/gzip helpers for the mod backend.
- `BazaarPlusPlus.Storage.dll`: SQLite schema, repositories, path interfaces, and local persistence models.
- `BazaarPlusPlus.Localization.dll`: localization resolution engine and language/mode helpers.

The optional BazaarAgent assemblies are:

- `BazaarPlusPlus.BazaarAgent.dll`: pure HTTP transport, action DTOs, validation, queues, and runtime controller.
- `BazaarPlusPlus.BazaarAgentHost.dll`: a separate BepInEx plugin that depends on BazaarPlusPlus, reads `BazaarAgentGameBridge`, and pumps the agent controller from Unity lifecycle methods (`src/BazaarPlusPlus.BazaarAgentHost/BazaarAgentHostPlugin.cs:16-63`).

The main source tree follows these boundaries:

- `Core/`: pure mod abstractions such as config, event bus, runtime service interfaces, run context, path contracts, and the run-snapshot contract (`IRunSnapshotProbe` plus its `RunBasicsSnapshot`/`PlayerStatsSnapshot`/`RankSnapshot` DTOs in `Core/GameState/`).
- `GameInterop/`: adapters over game, Unity, or publicized runtime surfaces, including client cache reads, static card data reads, the shared GameData day-tier resolver (`GameInterop/DayTiers/`), encounter status probes, the run snapshot probe (`GameInterop/RunSnapshot/` — the only place `Data.Run`/rank/leaderboard reads happen for RunLogging and Screenshots), live card snapshots, item-board preview adapters, native game-font access (`GameInterop/Fonts/`), and BazaarAgent cross-plugin facades.
- `Game/`: feature workflows, UI, user-facing policy, filtering, upload orchestration, storage use, and BPP-owned domain modules such as PvP battle evidence. Record construction for run logs and screenshots is pure mappers (`RunLogRecordMapper`, `RunScreenshotRecordMapper`) consuming probe snapshots.
- `Patches/`: Harmony patches. Patches reach services through `BppPatchHost`, not constructor injection (`src/BazaarPlusPlus/Patches/BppPatchHost.cs:7-24`).
- `Infrastructure/`: cross-cutting logging, UI tokens, stable text helpers, and shared non-feature utilities. The generic `RemoteEmbeddedCatalog<T>` owns cache → embedded → remote loading, 20-hour freshness policy, single-flight warm/refresh operations, per-caller cancellation over shared flights, typed outcomes, atomic cache writes, retry re-arming, monotonic publication, and lifetime-cancelled/generation-guarded disposal. A queued cold-start refresh takes ownership atomically when its refresh flight begins; canceling the originating warm flight before that handoff prevents the remote operation. Feature observers are serialized against disposal on a separate gate, so `TryGet` never waits for feature-side logging or index rebuilds (`src/BazaarPlusPlus/Infrastructure/RemoteEmbeddedCatalog/RemoteEmbeddedCatalog.cs`; contracts and adapters are alongside it). Other generic seams include `AtomicFileWriter`, `AsyncLoadCache<TKey,TValue>` (in-flight-deduped negative-caching async loads; hero/encounter portrait providers are thin facades over it), and `FileBackedPayloadStore<T>` (battleId-keyed atomic MessagePack payload files; the combat-replay and ghost payload stores are name-pinned facades over it). Operational logging is governed: features emit through closed `BppLogFeatureScope`s with dotted-snake event ids and typed privacy/cardinality/correlation fields, declared in per-feature `[BppLogEventSource]` `*LogEvents` classes discovered and validated by `BppLogEventCatalog`; Debug events compile out of Release (`src/BazaarPlusPlus/Infrastructure/Logging/Core/BppLogSchema.cs`, ratcheted by `tests/Architecture.Tests/LoggingGovernanceTests.cs`).

Architecture tests ratchet these boundaries, including `Core/` layering, shared item-board preview ownership, BazaarAgent isolation, voice-subtitle guards, and source layout (`tests/Architecture.Tests/CoreLayeringTests.cs`; Core layering starts at `:30`). Behavioral guarantees of the composition registries (feature start/stop fault isolation, mount ordering) are pinned by `tests/CompositionRuntime.Tests/`; `BppMountableRegistry.MountAll` deliberately has no per-item fault isolation (pinned as current behavior, unlike `BppFeatureRegistry`).

## Data And File Locations

Runtime data that BazaarPlusPlus owns is rooted under the game directory's `BazaarPlusPlusV4` folder. `BepInExPathProvider.Initialize()` sets the SQLite database path, combat replay payload directory, screenshot directory, combat replay video directory, and plugin directory (`src/BazaarPlusPlus/Core/Paths/BepInExPathProvider.cs:18-41`).

The local SQLite schema is versioned in `RunLogSchema`. The current local database schema version is `18` (v18 added replay battle item/skill counts plus player income/gold), row schema version is `11`, and upload payload schema version is `6` (`src/BazaarPlusPlus.Storage/RunLog/RunLogSchema.cs:10-14`). The schema creates runs, run events, battles, battle snapshots, run screenshots, combat replay videos, sync cursors, run sync state, and BazaarDB snapshot upload state plus indexes (`src/BazaarPlusPlus.Storage/RunLog/RunLogSchema.cs:57-272`).

## Event Flow

The plugin uses an in-memory event bus for decoupled runtime coordination. `RunLifecycleModule`, `CombatReplayModule`, `CombatStatusBarModule`, `VoiceSubtitlesInteropModule`, `VoiceSubtitlesModule`, and `RunLoggingModule` are feature modules registered at startup (`src/BazaarPlusPlus/BppComposition.cs`). The combat status bar subscribes to `CombatSimObserved` and `CombatFrameAdvanced`; it stores the latest message id/outcome in run context and advances the HUD frame count from replay events (`src/BazaarPlusPlus/Game/CombatStatusBar/CombatStatusBarModule.cs:25-55`).

PvP battle evidence is a shared `Game/PvpBattles` module, not a `GameInterop` adapter. It captures local/opponent identities and board snapshots from live game state and net messages (`src/BazaarPlusPlus/Game/PvpBattles/PvpBattleSnapshotCollector.cs:16-66`). `RunLoggingModule` is the feature-owned event intake: `Start` creates its replicated/queued store chain and session manager only after composition construction succeeds, subscribes once to run lifecycle, run initialization, PvP recording, and replay-drained events, then maps a matching `PVPCombat` manifest directly to persistence. Battles attach to the stable active/deferred run id before the event append and checkpoint. Interrupted runs remain resumable; normal completion owns an active, cancellable two-second replay-persistence deadline, and Stop is a quiescence barrier that forces any deferred completion before unsubscribing and disposing the store (`src/BazaarPlusPlus/Game/RunLogging/RunLoggingModule.cs`). No Run Logging `MonoBehaviour` is mounted.

## Encounter Preview

`EncounterPreviewModule` is the single owner of event, encounter-step, and hero-level preview semantics. Its typed query interface accepts only stable template ids/current level plus native text already present at the patch boundary; the module reads the current static-data source, hero, inventory, one generation-matched day-tier result, and native keyword typography through `IEncounterPreviewGameRuntime` (`src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewModule.cs`, `src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewGameRuntime.cs`). It owns cache identity/read/write, plan compilation, generation publication, dynamic evaluation, localization, and final presentation. Event, encounter-step, and hero-level queries all resolve to the single `EventPreviewResult` record (`src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewModule.cs:27-36`). Beginning a source generation first removes the old snapshot; generation checks prevent a superseded load from publishing, while a successful compile remains published with degraded status if its cache write fails (`src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewModule.cs:110-241`, `src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewPlanRegistry.cs:14-97`).

`EventPreviewStaticDataObserver` is only the Unity frame adapter that reports a newly ready source to the module (`src/BazaarPlusPlus/Game/EventPreview/EventPreviewStaticDataObserver.cs:7-16`). Tooltip patches receive the module through the `BppPatchFeatures` bundle and consume semantic results; they do not read plans, static-data maps, inventory, or CollectionPanel formatters (`src/BazaarPlusPlus/Patches/BppPatchFeatures.cs:7-16`, `src/BazaarPlusPlus/Patches/Tooltips/EncounterEventTooltipPatch.cs:67-90`, `src/BazaarPlusPlus/Patches/Tooltips/HeroLevelRewardsTooltipPatch.cs:61-66`). `CardAbilityValueReader` centralizes the shared reflection seam over game-authored ability/aura action and attribute values; Event Preview and Collection keep their separate localization and typography policies (`src/BazaarPlusPlus/GameInterop/Cards/CardAbilityValueReader.cs:13-153`, `src/BazaarPlusPlus/Game/EventPreview/EventPreviewLocalization.cs:11-45`, `src/BazaarPlusPlus/Game/CollectionPanel/Data/CollectionLocalizationResolver.cs:16-39`). `GameDataDayTierResolver` is the shared GameInterop owner for Collection and Event Preview: it resolves the active manager reference, `GameModeId`, and run day into a normalized positive-finite distribution plus the highest usable Bronze-to-Diamond tier; it exposes typed unavailable states, caches successes only within one manager generation, retries transient readiness, and rejects an Event Preview query whose plan source is no longer the current manager (`src/BazaarPlusPlus/GameInterop/DayTiers/`).

## Overlay Panels

`Game/OverlayPanels/OverlayPanelHost.cs` is the single Unity adapter that owns main-overlay-panel lifecycle: it reads per-frame input (escape, panel toggle hotkeys, combat state, scene changes), runs the pure `OverlayLifecycleCore` rules, and dispatches open/close/tick to registered panels (`src/BazaarPlusPlus/Game/OverlayPanels/OverlayPanelHost.cs:12-45`). It mounts before every panel mount, and CollectionPanel, HistoryPanel, and LiveBuildPanel all register through its accessor, enforcing at-most-one-open-panel (`src/BazaarPlusPlus/BppComposition.cs:162-185`). Lifecycle tests live in `tests/OverlayPanelLifecycle.Tests/`.

## Collection Panel

CollectionPanel is a full-screen Item/Skill catalog mounted by `CollectionPanelMount`, registered with the shared Overlay Panel Host (`src/BazaarPlusPlus/BppComposition.cs`). Its filter state is pure mutable data: active tab/card type, nullable concrete `SelectedHero` (`EffectiveHero` falls back to `Common`), tiers, tags, hidden keyword tags, Any/All facet modes, sizes, selected source key, run-day filter, and sort priority (`src/BazaarPlusPlus/Game/CollectionPanel/Data/CollectionFilterState.cs`). The tab model contains only `Items` and `Skills` (`src/BazaarPlusPlus/Game/CollectionPanel/Data/CollectionTabKind.cs:6-15`).

All filter, search, and catalog state transitions are centralized in the pure `CollectionViewState` reducer: panel command methods are single-line forwards, each returning a `CollectionRenderOutcome?` (`null` = same-value no-op) that the panel consumes at its single `ApplyOutcome` point; grid read-back goes through the injected `ICollectionGridPort`, and hero normalization on catalog accept never writes the hero preference (`src/BazaarPlusPlus/Game/CollectionPanel/CollectionViewState.cs`; behavior tests in `tests/CollectionViewState.Tests/`; load-bearing contract points in ADR-0011).

Collection creates one native-card-preview scope for each Unity runtime and gives its virtualizer only that scope. Realized cells retain opaque sessions, not native component/kind/setup-task tuples; stale acquisitions are disposed immediately (`src/BazaarPlusPlus/Game/CollectionPanel/CollectionPanel.cs:646-655`, `src/BazaarPlusPlus/Game/CollectionPanel/Grid/CollectionGridVirtualizer.cs:37-46`, `src/BazaarPlusPlus/Game/CollectionPanel/Grid/CollectionGridVirtualizer.cs:385-470`). Runtime teardown waits for pending binds and scope disposal before destroying the overlay and Collection-owned art/material caches (`src/BazaarPlusPlus/Game/CollectionPanel/CollectionPanel.cs:543-625`). Collection-specific tooltip registry, cache refcount, and shared-material cleanup remain in its owner adapter and destroy patch, outside the generic preview host.

Cell measure/fit is split out of the virtualizer: `CollectionCardFitMath` is pure fit math (scale plus anchored position), `NativeCardCellFitter` is the Unity measurement adapter (frame-container → raw-image → aspect-fallback → rect chains), and `NativeCardCellBoundsCache` caches per-cell visual bounds with three invalidation hooks (rebind, scale-dirty, art-load completion) so the scroll path repositions with `allowMeasure: false` instead of remeasuring every realized cell each frame (`src/BazaarPlusPlus/Game/CollectionPanel/Grid/CollectionCardFitMath.cs`, `.../NativeCardCellFitter.cs`, `.../NativeCardCellBoundsCache.cs`, `.../CollectionGridVirtualizer.cs:243`).

Filtering is code-owned and deterministic. `CollectionFilterEngine.Apply()` applies active card type, excludes package cards from normal results, applies source offer pool membership, hero, tier, day, tag, keyword, and size filters, then sorts by tier/size priority plus localized display name (`src/BazaarPlusPlus/Game/CollectionPanel/Data/CollectionFilterEngine.cs:15-80`). Tag and keyword facets support `Any` and `All` matching (`src/BazaarPlusPlus/Game/CollectionPanel/Data/CollectionFilterEngine.cs:99-135`), and the UI exposes mode toggles in the tag and keyword headers (`src/BazaarPlusPlus/Game/CollectionPanel/Ui/CollectionPanelView.Tree.cs:173-199`).

The Day gate consumes only the shared GameData result's `MaximumTier`; absent, not-ready, missing, invalid, and out-of-run results fail open. The manual Tier filter remains an independent AND condition, fixed-tier sources suppress only the Day gate, and Legendary starting tiers retain the game's Diamond compatibility alias (`src/BazaarPlusPlus/Game/CollectionPanel/Data/CollectionFilterEngine.cs`, `src/BazaarPlusPlus/Game/CollectionPanel/Data/CollectionFilterContext.cs`).

Merchant and trainer source filtering is driven by an embedded `collection-sources.json` catalog. The current `CollectionSourceCatalog.ExpectedSchemaVersion` is `4`; mismatched JSON versions are rejected during build/parse (`src/BazaarPlusPlus/Game/CollectionPanel/Sources/CollectionSourceCatalog.cs:15`, `src/BazaarPlusPlus/Game/CollectionPanel/Sources/CollectionSourceCatalog.cs:116-124`). Each source has `offerSegments`, and each segment parses a typed rule with hero mode, starting tier, sizes, tags, hidden tags and groups, enchantability, and enchantment facets (`src/BazaarPlusPlus/Game/CollectionPanel/Sources/CollectionSourceCatalog.cs:259-351`).

Card VMs project base card tags and per-enchantment facets from game templates. Lifesteal is derived when an item has positive Lifesteal base value at any tier even if the template lacks the hidden tag (`src/BazaarPlusPlus/Game/CollectionPanel/Data/CollectionCardVm.From.cs:24-45`, `src/BazaarPlusPlus/Game/CollectionPanel/Data/CollectionDerivedKeywordFacts.cs:20-37`).

## History Panel, Item Boards, And Live Build

HistoryPanel is mounted through `HistoryPanelMount` with a single-constructor `HistoryPanelDependencies` (run state, data service, replay service, optional probe/link surfaces, and the combat-replay directory path as a plain string); run state is the read-only two-member `IHistoryPanelRunState` (`IsInGameRun`, `CurrentServerRunId`) adapting `IRunContext` (`src/BazaarPlusPlus/Game/HistoryPanel/IHistoryPanelRunState.cs:10-32`, `.../HistoryPanelDependencies.cs:11`). It renders battle previews by asking the shared item-board preview renderer to render a projected board and handling preview phases (`src/BazaarPlusPlus/Game/HistoryPanel/HistoryPanel.cs:225-243`, `:340-357`).

HistoryPanel's right rail contains local database status, remote server health probing, runs/ghost tabs, ghost filters, delete/replay controls, status text, and a collapsible BazaarDB account-link card (`src/BazaarPlusPlus/Game/HistoryPanel/Ui/HistoryPanelUiToolkitView.Tree.cs:356-410`). The account-link card POSTs a one-time code to the bazaardb.gg redeem endpoint through `BazaarDbLinkClient`, built at startup on a dedicated 30s-timeout HttpClient independent of the mod-api base URL (`src/BazaarPlusPlus/Plugin.cs:219-227`), with link state persisted by `Game/HistoryPanel/AccountLink/BazaarDbAccountLinkStore.cs`. Server health display state is derived from the mod API health probe result without changing storage state (`src/BazaarPlusPlus/Game/HistoryPanel/HistoryPanelServerHealth.cs:51-81`).

`GameInterop/ItemBoardPreview` is the shared board-rendering adapter for HistoryPanel and LiveBuildPanel. `BppItemBoardSlotPlanner` plans cards onto a 10-socket board, with special handling for selectable shop/container boards (`src/BazaarPlusPlus/GameInterop/ItemBoardPreview/BppItemBoardSlotPlanner.cs:10-24`). Its surface owns only an injected native-preview host, a per-surface scope, and opaque sessions; its canvas remains `ScreenSpaceOverlay` per ADR-0003 (`src/BazaarPlusPlus/GameInterop/ItemBoardPreview/ItemBoardPreviewSurface.cs:15-42`, `src/BazaarPlusPlus/GameInterop/ItemBoardPreview/ItemBoardPreviewSurface.cs:333-353`, `src/BazaarPlusPlus/GameInterop/ItemBoardPreview/ItemBoardPreviewSurface.cs:749-828`).

## Native Card Preview

`GameInterop/CardPreview` is the owning module for native card prefab selection, instantiation, setup/resize, reflection, hover state, tooltip replacement, pooling, and destruction. Production callers see only `INativeCardPreviewHost`, a per-owner `INativeCardPreviewScope`, and opaque `INativeCardPreviewSession` intent operations (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewContracts.cs:12-45`). Each scope has its own pool: closing rejects new acquisitions, cancels and waits outstanding setup, invalidates/destroys active sessions, then destroys idle objects; a session released after closing cannot re-enter the pool (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewHost.cs:205-357`, `src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewScopeLifetime.cs`).

Successful acquisition means the game template was resolved, a synthetic instance was built, the owner prepared the inactive prefab, and native setup plus resize completed before the session was delivered (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewFactory.cs`). The host also owns complete presentation visibility: the game's `CardPreviewBase.Show` covers only art/frame, so item gem groups remain concealed through setup and cancellation, are revealed only after a successful session `Show`, and are always concealed by `Hide` (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewPresentation.cs`, `src/BazaarPlusPlus/GameInterop/CardPreview/NativePreviewPresentationTransaction.cs`). Tooltip modifier refresh is a typed host transaction: it verifies that the visible primary tooltip belongs to the hovered session, creates and writes replacement data, re-hovers, and attempts to restore the old data/tooltip if a write or re-hover fails; an impossible rollback returns a typed failure (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewHost.cs`, `src/BazaarPlusPlus/GameInterop/CardPreview/NativeTooltipRefreshTransaction.cs`). Concrete pool/runtime/reflection/resource types are confined to this owning module by `NativeCardPreviewArchitectureTests`.

LiveBuildPanel reads live shop, board, and stash cards through `LiveCardSnapshotReader` (`src/BazaarPlusPlus/GameInterop/LiveCards/LiveCardSnapshotReader.cs:21-35`). Its feature-owned parser, queries, logging policy, and manual-refresh policy remain under `Game/LiveBuildPanel/Recommendations`, while the shared remote/embedded lifecycle is supplied as `IRemoteEmbeddedCatalog<TenWinBuildCorpus>`. `BppComposition` owns that catalog for the plugin lifetime and injects one repository through `LiveBuildPanelMount`; the panel never constructs the repository or loader (`src/BazaarPlusPlus/BppComposition.cs`, `src/BazaarPlusPlus/Game/LiveBuildPanel/LiveBuildPanelMount.cs`, `src/BazaarPlusPlus/Game/LiveBuildPanel/LiveBuildPanel.cs`). The embedded seed is supplied by the shared remote-data build pipeline rather than a checked-in JSON file (`src/BazaarPlusPlus/RemoteEmbeddedData.targets:27-31`). The panel exposes a once-per-session manual final-build refresh action; failures do not consume that allowance, the first successful pull reports Updated, and only an already-consumed pull reports NoChange (`src/BazaarPlusPlus/Game/LiveBuildPanel/Recommendations/BuildRecommendationRefreshService.cs`, `src/BazaarPlusPlus/Game/LiveBuildPanel/Recommendations/BuildRecommendationRepository.cs`).

## Combat Replay And Video

Combat replay records local PvP battle replay payloads and lets HistoryPanel start playback when a local or downloaded ghost replay payload is available. Video recording is optional and gated by async GPU readback support, a resolvable FFmpeg binary, and output directory configuration (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayRecordingGate.cs:33-60`).

Saved-replay playback state algebra lives in the pure `SavedReplayLifecycle` core: staged start commits, the 15-second exit-suppression latch shared by the continue/bootstrapped-exit/native-exit paths, the two-phase exit decision around the ended-publish, pending menu-return polling (a state parallel to start progress), and startup-interruption relay. `CombatReplayRuntime` is its translation layer — it executes publishes, portrait cleanup, and menu dispatch but holds no transition logic (`src/BazaarPlusPlus/Game/CombatReplay/SavedReplayLifecycle.cs`; behavior tests in `tests/CombatReplayPlaybackLogging.Tests/SavedReplayLifecycleTests.cs`; contract points in ADR-0011).

When recording starts, `CombatReplayVideoRecorder` creates a capture session, stores temp/final output paths, starts audio taps, suppresses selected BPP chrome, saves start metadata, and starts the capture coroutine (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoRecorder.cs:525-566`). Audio capture is additive: capture failure does not abort video recording. The recorder derives a WAV path, starts the platform capture tap if available, and logs/cleans up on failure (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoRecorder.cs:582-643`). On playback end, it closes the audio taps, retains only usable sample-bearing WAVs, freezes the finalization inputs into detached contexts, dispatches encoder drain/audio mux/metadata completion off the main thread, and clears the active state so a later replay cannot overwrite those inputs (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoRecorder.cs:220-282`, `src/BazaarPlusPlus/Game/CombatReplay/Audio/ReplayAudioTapStopper.cs:12-27`, `src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoRecorder.cs:331-381`, `src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoRecorder.cs:1141-1160`).

BPP UI chrome suppression is centralized in `Game/OverlayPanels`. Screenshot mode hides CollectionPanel dock, settings dock, and combat status bar; replay recording mode hides CollectionPanel dock and settings dock while intentionally leaving the combat status bar visible (`src/BazaarPlusPlus/Game/OverlayPanels/BppUiChromeSuppression.cs:13-25`).

## Screenshots, Uploads, And Ghost Battles

End-of-run capture is one run-scoped `EndOfRunCaptureWorkflow`: its core owns generation, summary readiness, automatic capture, the bounded pre-frame retry budget, reveal/frame/metadata deadlines, artifact validation, metadata persistence, late-artifact cleanup, Continue blocking, and the single terminal outcome (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCaptureWorkflowCore.cs`). Readiness requires native reveal start, a cleared screen transition, settled skills, and either 500 ms of structural card-pose stability after observed motion or the native `FaceUp` completion fallback; empty card boards retain their native settled path. The private `EndOfRunCaptureDriver` is the Unity/native surface adapter for lifecycle signals, throttled screen discovery, card-hierarchy sampling, next-loop/end-of-frame capture scheduling, and BPP chrome suppression (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCaptureDriver.cs`). Continue stays blocked only until the settled frame's RGBA pixels have been copied out of Unity; PNG encoding, atomic file write, and metadata persistence then continue in the background without consuming or replaying the native click. Composition constructs the workflow and exposes its two-intent interface to patches before mounting that driver, so the Continue and raw reveal patches fail open during startup and teardown (`src/BazaarPlusPlus/BppComposition.cs:139-145`, `src/BazaarPlusPlus/BppComposition.cs:199-204`, `src/BazaarPlusPlus/Patches/EndOfRun/EndOfRunScreenshotPatch.cs:8-22`, `src/BazaarPlusPlus/Patches/EndOfRun/EndOfRunSummaryRevealPatch.cs:7-24`). A verified PNG is never deleted or recaptured when metadata persistence fails or times out; a late artifact from a capture canceled before frame acquisition is deleted (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCaptureWorkflowCore.cs`).

Uploads are consolidated behind an `IUploadFeed` seam: `UploadPumpMount` mounts two `BackgroundUploadPump` components, one draining `BazaarDbSnapshotUploadFeed` (optional, keyed by the current profile account id) and one draining `RunBundleUploadFeed` (`src/BazaarPlusPlus/Game/Upload/UploadPumpMount.cs:22-29`), with `StartupUploadAttemptGate`/`StartupUploadAttemptRunner` handling the startup catch-up attempt (`src/BazaarPlusPlus/Game/Upload/StartupUploadAttemptGate.cs`). `IUploadFeed.Activate(services, logState, cadence)` returns an `IUploadFeedSession` (`IsEnabled`, `RunAttemptAsync`, `SubscribeArmSignals`); the pump passes its real cadence, sessions own their attempt resources, and settings rows request an immediate attempt by publishing `UploadArmRequested(UploadFeedKind)` on the event bus rather than through a static registry. Disposal is two-point: arm subscriptions release first in `OnDestroy`, and the session disposes only after the shutdown drain callback (`src/BazaarPlusPlus/Game/Upload/IUploadFeed.cs:109-124`, `.../BackgroundUploadPump.cs:82-104`; ADR-0011).

Run and replay uploads use the mod API client and local storage state; PTR runs are excluded at the feed level (see §Game Build Channel). Ghost battle sync imports remote battle data into local history storage; server-side behavior is outside this repository and should not be treated as code-verified here.

## Tooltip Preview, Settings, And Hotkeys

Enchant preview visibility is a three-state setting controlled by `PreviewVisibilityMode`: `Off`, `AutoOnPedestalChoice`, and `Always`. `ItemEnchantPreviewSettingsDockEntry.Create()` supplies its cycle order (`Off → AutoOnPedestalChoice → Always`), and `BppSettingsDockCatalog.ResolvePreviewVisibilityModeStatus` its status labels (`src/BazaarPlusPlus/Game/ItemEnchantPreview/ItemEnchantPreviewSettingsDockEntry.cs:9-29`).

Settings-dock rows themselves are data: every cycling or boolean row is a `CyclingSettingsDockEntry<T>` (with a `Toggle` factory for the bool case) built by a per-feature static factory supplying order, key, value ladder, read/write delegates, highlight predicate, status text, and an optional `onChanged` hook (`src/BazaarPlusPlus/Game/Settings/CyclingSettingsDockEntry.cs`). Only the history-panel action button and the force-lockable end-of-run screenshot toggle remain hand-built definitions.

`TooltipPreviewModePolicy` owns preview priority. Upgrade hotkey wins first, then enchant hotkey, then enchant `Always`, then enchant `AutoOnPedestalChoice` only when the current choice pedestal is an enchant pedestal (`src/BazaarPlusPlus/Game/Tooltips/TooltipPreviewModePolicy.cs:52-74`). A `TooltipModifierRefreshController` mountable re-resolves open preview tooltips when the Ctrl/Shift hold state changes; hovered synthetic previews delegate a typed refresh request to the Native Card Preview host, while ordinary game-card tooltips keep the native-controller path (`src/BazaarPlusPlus/Game/Tooltips/TooltipModifierRefreshController.cs:25-36`, `src/BazaarPlusPlus/Game/Tooltips/TooltipModifierRefreshController.cs:105-177`). The tooltip patch surface also covers encounter/event tooltips (gated by the `Game/EventPreview` settings toggle), quest reward previews and aggregate-item missing types (separate implementations sharing the default-off `QuestPreview/Enabled` gate), and hero level rewards (`src/BazaarPlusPlus/Patches/Tooltips/`). Disabling Quest Preview immediately restores tracked native quest text/layout and hides its pooled aggregate-item sections. Mod-appended text is rendered through the shared `BppTooltipSections` helper. Sections keep the cloned native donor typography and attach the game's own zh-CN fallback chain only when BPP-authored content contains CJK (`src/BazaarPlusPlus/Patches/Tooltips/BppTooltipSections.cs:12-15`, `src/BazaarPlusPlus/Patches/Tooltips/BppTooltipSections.cs:55-76`).

BPP hotkeys are user-rebindable and persisted in config per action. `BppHotkeyActionId` covers five actions: the two hold-preview hotkeys (Ctrl enchant / Shift upgrade defaults) plus toggles for CollectionPanel, LiveBuildPanel, and HistoryPanel (`src/BazaarPlusPlus/Game/Input/BppHotkeyActionId.cs`); rebinding rows are cloned from native settings rows (`src/BazaarPlusPlus/Game/Input/BppKeyBindRowController.cs`), and panel toggle presses are resolved per frame by the Overlay Panel Host. Binding-path normalization, ctrl/shift alias expansion, conflict detection, and the default/display data tables are the pure `HotkeyBindingPathCore` (`src/BazaarPlusPlus/Game/Input/HotkeyBindingPathCore.cs`, compile-linked into the zero-ManagedPath `tests/HotkeyBindingPath.Tests/`); `BppHotkeyService` remains the Unity/config facade. Binding paths in `BazaarPlusPlus.cfg` `[Hotkeys]` are untrusted input: junk normalizes to empty and falls back to the action default. The conflict check compares BPP actions only against other BPP actions, not native `Gameplay/*` bindings.

The settings dock registers all feature rows through `SettingsDockEntryRegistry` with order constants centralized in `BppSettingsDockOrder` (`src/BazaarPlusPlus/Game/Settings/BppSettingsDockOrder.cs`); the roster spans history, name override, bilingual item names, legendary position, enchant preview, event and quest previews, combat status bar, Chinese locale, supporter list, voice subtitles, end-of-run screenshot, and BazaarDB upload (`src/BazaarPlusPlus/BppComposition.cs:119-137`). There is no BPP font selector because all BPP-owned game UI follows the game's font assets.

## Localization And Fonts

`BazaarPlusPlus.Localization` is the localization resolution engine. The `L` facade is installed at plugin startup with language and locale-mode providers, then resolves `LocalizedTextSet` values against current language and Chinese locale mode (`src/BazaarPlusPlus.Localization/L.cs:11-30`, `src/BazaarPlusPlus/Plugin.cs:185-196`).

BPP does not embed, extract, select, or create an operating-system font. Every feature calls the single `NativeGameTypography` adapter and never receives a raw `Font`, `TMP_FontAsset`, fallback chain, or `PanelTextSettings`. The adapter keeps the renderer-specific implementation private: native TMP labels retain their donor primary font and material while a cloned primary receives the corresponding game fallback chain; BPP-created uGUI uses an opaque prepared binding over the game's loaded sans primary plus the complete ordered `zh-CN` Static → SecondSet → Dynamic chain; UI Toolkit uses a panel-local scope over the Dynamic asset's packaged `UnityEngine.Font` source because it cannot consume TMP assets directly (`src/BazaarPlusPlus/GameInterop/Fonts/NativeGameTypography.cs`).

`PrepareOwnedText` preserves fail-before-create behavior for BPP TMP trees. `EnsureNativeTextCoverage` augments donor TMP without exposing how the chain is selected. `TryAttachPanel` atomically installs a panel-local `PanelTextSettings` bound to the game's sans body font; its scope is the only code that sets both `unityFont` and `unityFontDefinition`, checks external text against the actual selected font, and releases the panel settings. OS and emoji fallback remain disabled, global game settings are never mutated, and all Unity mutation is guarded to the initialization thread. The adapter restores donors, prunes destroyed donor bindings, invalidates outstanding scopes, and releases every owned handle/clone at teardown (`src/BazaarPlusPlus/GameInterop/Fonts/NativeGameTypography.cs`).

## Voice Subtitles

`Game/VoiceSubtitles` renders in-game voice-over subtitles (the BazaarLine integration): `VoiceSubtitlesModule` plus a `GameInterop/VoiceSubtitles` bridge module observe game VO playback (`src/BazaarPlusPlus/BppComposition.cs`), and `VoiceLineDisplayDispatcher`/`VersionLabelScanner` mountables render cues. The line catalog is supplied under its stable manifest name by the shared remote-data build pipeline; `VoiceLinesCatalogFactory` contributes the parser and feature logging policy to `RemoteEmbeddedCatalog<VoiceLine[]>` (`src/BazaarPlusPlus/RemoteEmbeddedData.targets:21-25`, `src/BazaarPlusPlus/Game/VoiceSubtitles/VoiceLinesCatalogFactory.cs`). The feature module owns this catalog for its own lifetime and disposes it before clearing the static line catalog, so a late remote continuation cannot republish after `Stop()` (`src/BazaarPlusPlus/Game/VoiceSubtitles/VoiceSubtitlesModule.cs`). The feature is gated by a master toggle (default OFF) in `BazaarPlusPlus.cfg` `[VoiceSubtitles]` (`src/BazaarPlusPlus/Game/VoiceSubtitles/VoiceSubtitlesGate.cs:8-11`, `src/BazaarPlusPlus/Core/Config/BppConfig.cs:98-103`), with a four-state Subtitle Mode dock row registered via `VoiceSubtitlesSettingsDockEntry.RegisterAll`. Subtitle labels preserve the version-label donor font/material when it already covers Chinese. If it does not, mounting waits until the game's Chinese font configuration exists, then renders the Chinese row through `TextMeshProUGUI` using the game sans primary clone with its complete Chinese fallback chain and without synthetic bolding (`src/BazaarPlusPlus/Game/VoiceSubtitles/VersionLabelScanner.cs:43-69`, `src/BazaarPlusPlus/Game/VoiceSubtitles/VoiceLineDisplay.cs`).

## Supporter Attribution

Supporter attribution is a game-side display module, not a generic sampling utility. `BPPSupporters.SampleMany()` and `Sample()` delegate to `BPPSupporterCatalog.GetCurrentEntries()` and `BPPSupporterSampler` (`src/BazaarPlusPlus/Game/Supporters/BPPSupporters.cs:13-31`). The catalog fetches `https://bpp-static.bazaarplusplus.com/supporter-list.json`, caches it in temp storage, and falls back to bundled placeholder entries if remote/cache reads fail (`src/BazaarPlusPlus/Game/Supporters/BPPSupporterCatalog.cs:14-25`, `src/BazaarPlusPlus/Game/Supporters/BPPSupporterCatalog.cs:47-82`).

HistoryPanel, CollectionPanel, and LiveBuildPanel consume supporter samples for attribution rows. Every prefix, name, separator, suffix, and action element pins both `unityFont` and `unityFontDefinition` to the same game source font so Latin and CJK names cannot diverge through a child theme font definition; supporter names use the font's normal weight rather than synthetic bold (`src/BazaarPlusPlus/Game/Supporters/Ui/BPPSupporterAttributionRow.cs`). This module should stay separate from feature-specific UI behavior.

## BazaarAgent Optional Host

BazaarAgent is optional. The host plugin declares `[BepInDependency(BppPluginMetadata.Guid)]`, reads `BazaarAgentGameBridge.Current`, creates a pure runtime controller, pumps it from `Update()`, and disposes it on destroy (`src/BazaarPlusPlus.BazaarAgentHost/BazaarAgentHostPlugin.cs:16-63`).

The host listens only on loopback. The default port is fixed at `127.0.0.1:47900`, with a 32 MiB cap for raw replay-record request bodies (`src/BazaarPlusPlus.BazaarAgent/Contract/BazaarAgentPorts.cs:8-22`, `src/BazaarPlusPlus.BazaarAgent/Transport/BazaarAgentHttpServer.cs:101`). Current routes are:

- `GET /v1/context`
- `POST /v1/actions`
- `POST /v1/replay/record`
- `POST /v1/replay/continue`

The action set (`POST /v1/actions`, current schema `2.2.0`, `src/BazaarPlusPlus.BazaarAgent/Contract/BazaarAgentDecision.cs:11`) includes two Flow actions beyond the basics: `ReturnToMenu`, emitted only in `EndRunVictory`/`EndRunDefeat` while the scene loader is not transitioning, advances the end-of-run screen back to hero-select via `RunManager.LoadMainMenu()` — closing the unattended `run → next run` loop; and `Continue` (ADR-0008), emitted only when a replay sits at `finishedAwaitingContinue`, routed to the same `CombatReplayRuntime.TryContinueReplay` facade so the agent stays replay-agnostic. `isClientBusy` reflects the real client state (`AppState.IsWaitingForServerResponse || AppState.BlockInput`).

Those routes are dispatched in `BazaarAgentHttpServer.HandleContextAsync()` (`src/BazaarPlusPlus.BazaarAgent/Transport/BazaarAgentHttpServer.cs:161-207`). Replay record accepts a raw binary GhostBattlePayload msgpack+gzip body and optional battle id from header/query before queueing a start command; replay continue queues an explicit continue command (`src/BazaarPlusPlus.BazaarAgent/Transport/BazaarAgentHttpServer.cs:353-395`).

## endpoint.json decision — remove it (verified 2026-06-05)

`endpoint.json` is a **vestigial discovery file with no active code consumer**, and removing it eliminates a whole risk class from the path rename. Evidence (live code, 2026-06-05):

- **Written/deleted only by the HTTP server.** `AutoBazaarHttpServer.WriteEndpointJson()`/`DeleteEndpointJson()` (`AutoBazaarHttpServer.cs:288-319`), called on `Start()`/`Stop()` (:65-74, :100-105). Path comes from `IAutoBazaarOptions.EndpointFilePath` = `DecisionLogRoot/endpoint.json` (`AutoBazaarBepInExOptions.cs:42-45`). It carries `{baseUrl, schemaVersion, pid}`.
- **No active code reader anywhere.** `rg -uu "endpoint.json"` across the *entire* `bpp/` workspace (mod + `bazaarplusplus-agent` + `bazaarplusplus-installer` + `bazaarplusplus-server` + `bazaarplusplus-site`) returns active-code hits only for the writer/deleter, the options path, and one test method asserting it is written during run and deleted after dispose (`AutoBazaarHttpServerTests.cs:300-318`). It also returns old/reference/generated docs describing the file and one unrelated third-party package string. **Zero active consumers.**
- **The documented "discovery" rationale is dead.** The doc frames it as a discovery file (`auto-bazaar-http-api-v1.md:15-29`), but the port is **config-driven with a fixed default `47900`** (`AutoBazaarBepInExOptions.cs:26-31`) — there is nothing to *discover*. The only design that ever needed it proposed an **ephemeral** port (`docs/superpowers/specs/2026-05-09-thin-mod-proxy-agent-controller-design.md:103-108`); that design was not shipped (the live server binds the fixed config port).
- **The external agent does not use it — or HTTP at all.** `bazaarplusplus-agent` is a **stdio JSONL** server (`serve_stdio`, `bazaar_agent/runtime/session.py:13`; read/write over stdin/stdout, `bridge/protocol.py:11,18`). Its only network client is the DeepSeek LLM call (`providers/deepseek.py:59`). The mod's loopback HTTP server and the stdio agent are **two separate transports**; nothing bridges them via `endpoint.json`.

**Decision (fold into WP-M + WP-3/4):** **delete `endpoint.json` write/delete + the `EndpointFilePath` port member**, and drop or rewrite the one test method that asserts its presence/deletion. Keep the HTTP server bound to the config port (default `47900`). This is the cleanest option among the three considered:

| Option | Effect | Verdict |
|---|---|---|
| **(a) Remove endpoint.json entirely** (chosen) | Server binds fixed/config port; no discovery file. Removes the `EndpointFilePath` port member + writer + the endpoint-file test. | **Recommended.** No active code consumer exists; removes the path-move risk class; shrinks the pure-core surface (`IAutoBazaarOptions`). |
| (b) Keep it, freeze its path | Pin `endpoint.json` at a stable location even as decision logs move. | Rejected — preserves a file nobody reads; the "stable path" guards a non-existent consumer. |
| (c) Different discovery mechanism (e.g. advertise port via a handshake) | New surface for a future external HTTP client. | Rejected — speculative; no client is planned (agent is stdio). Revisit only if an HTTP-discovery client is ever built. |

Because (a) is chosen, the on-disk path rename in WP-M relocates **only `decisions.jsonl`** (developer-facing diagnostics), not a discovery file an external tool might poll.

## Target end state (human-confirmed)

The subsystem is renamed **BazaarAgent**, and **BazaarAgent holds all automation business logic** while consuming BazaarPlusPlus as a game-interop substrate — with these **confirmed decisions**:

1. **Two plugins.** `BazaarPlusPlus.dll` **stays the main plugin, role unchanged**, and merely *adds* a small public game-interop facade. A **new assembly `BazaarPlusPlus.BazaarAgentHost.csproj`** carries its own `[BepInPlugin]` + `[BepInDependency(<BazaarPlusPlus GUID>)]`, references `BazaarPlusPlus.dll` + the pure core + the game DLLs, and **self-mounts** (its `BaseUnityPlugin` is itself a `MonoBehaviour`, hosting `Update()`/`OnDestroy()`). The `#if BPP_BAZAARAGENT_HOST` registration in `BppComposition` is **deleted**. BazaarPlusPlus **no longer references the agent module at all** → no cycle.
2. **Dedicated public facade** for visibility — *not* blanket-public, *not* `InternalsVisibleTo`. Introduce a narrow public game-interop surface; keep everything else `internal`.
3. **Config migrates** to the host plugin's own `<GUID>.cfg`, **and** the section is renamed `[AutoBazaar]` → `[BazaarAgent]`. This is **behavior-affecting**: both the file move and section rename rebind `Enabled` (default `false`) and `HttpListenerPort` (default `47900`), so any user who set `[AutoBazaar] Enabled=true` or a custom port in `BazaarPlusPlus.cfg` has those silently reset. Carry this in **WP-M** with a release note — **not** in the mechanical WP-R.
4. **Preserve the pure core.** `BazaarPlusPlus.BazaarAgent.dll` stays `System` + `Newtonsoft.Json` only (keeps the fast `net10.0` isolation tests in `tests/BazaarAgent.Tests` that reference only the core csproj). All game/Unity/BepInEx/Harmony coupling lives in the new host assembly.
5. **CombatReplay coupling** is replaced by an event-bus / `Func<>` probe (the repo's established cross-feature pattern), **not** by promoting `CombatReplayRuntime` to public — it is only one transient bool.
6. **Omittability** is redesigned as **two independent top-level deliverables**: a default mod build ships only `BazaarPlusPlus.dll`; the host plugin is an on-demand build artifact. **Physical optionality must survive a prior host build:** after inversion BazaarPlusPlus no longer references the agent module, so it must still *actively scrub* both new artifacts (`BazaarPlusPlus.BazaarAgentHost.dll` + `BazaarPlusPlus.BazaarAgent.dll`) from the live plugin folder and installer payloads on a default build — mirroring today's delete-then-conditionally-copy pattern. This is **guarded by a new build/architecture test** (WP-5).
7. **Major version bump** + a **superseding ADR**. Expect `CLAUDE.md`'s assembly narrative and the `docs/reference/auto-bazaar-*.md` filenames to need updating.
8. **Rename `AutoBazaar` → `BazaarAgent` repo-wide** per the two-bucket Naming map at the top: the **code-only** bucket (assemblies, namespaces, all `AutoBazaar*` types, directories, compile symbol/MSBuild prop, run.sh flag, internal log tag, docs) lands behavior-neutral in **WP-R**; the **user-visible** bucket (cfg section, on-disk path segment) lands behavior-affecting in **WP-M** with a release note. Wire field names stay. The external `bazaarplusplus-agent` repo is **out of scope** (wire is keyed on JSON field names, not type names).

## Alternative approaches to the overall goal (for the human to weigh — confirmed direction is full inversion)

The user's intent is two-fold: (1) rename, and (2) "BazaarAgent owns its automation as a cleanly-separated concern." The **confirmed** path is full plugin-inversion (two plugins). These are presented as **alternatives for the human**, not a recommendation to overturn — but they bound the risk of the confirmed path. The audit's own §一/§八 conclusion is that the *encapsulation* intent is **already met today** by the ADR-0005 ports, so the marginal value of inversion is the **independent-plugin/independent-packaging** capability, not "cleaner ownership" per se.

| Approach | What it delivers | Cost / risk | When it's the right call |
|---|---|---|---|
| **A. Rename-only (WP-0 + WP-R, optionally a separately approved WP-M)** | The `BazaarAgent` code name everywhere plus WP-0 smell cleanup. If the human explicitly wants the user-visible migration without inversion, WP-M can be repackaged as its own release-note + in-game-validation change. **No dependency inversion**, no second plugin. | Lowest structural risk. No ADR overturn, no facade, no cross-plugin handshake, no build-graph flip. If WP-M is included, it still resets cfg/path state and removes endpoint.json, so it is not a mechanical rename. | If the real ask was "make the name right + stop the host smells," and independent packaging is **not** actually needed. The audit argues encapsulation is already achieved by the ports, so this may satisfy the intent at a fraction of the cost. |
| **B. Rename + WP-0 cleanup only (no cfg/path move)** | Just the code rename + smell cleanup; cfg section and on-disk path stay `AutoBazaar`. | Even lower risk — zero user-visible change, no release-note migration. | If you want the cleaner code names now and are unwilling to reset any user's `Enabled`/port. (The names users see in `.cfg`/on disk would then diverge from the code — a minor wart.) |
| **C. Full inversion, two plugins (CONFIRMED)** | BazaarAgent becomes its own `[BepInPlugin]` referencing BazaarPlusPlus as a game-interop library; independent build/packaging deliverable. | Highest: supersede ADR-0005, new public facade, cross-plugin handshake (`[BepInDependency]` + static accessor or stateless reader), build-graph flip, existing architecture tests rewritten + 1 new scrub guard, new cross-plugin per-frame race surface (mitigated by the WP-0 CombatReplay cut), major-version bump. | If independent-plugin / independent-distribution of the agent is a real product requirement — the named ADR-0005:18 reopen condition. **This is the confirmed direction.** |
| **D. Third thin entry assembly** | A new tiny `[BepInPlugin]` references both BazaarPlusPlus and the agent core, breaks the cycle without making the agent self-host. | Adds an assembly; the agent still isn't "its own plugin," so it doesn't deliver independent-plugin identity. Audit §四 lists it as a cycle-breaker but notes it adds assembly count without the ownership win. | Rarely — only if you want to avoid a public facade on BazaarPlusPlus but still break the cycle. Inferior to C for the stated intent. |

**Recommendation framing for the human:** if "independent BepInEx plugin / independent packaging of the agent" is a genuine need, proceed with **C** (this plan). If the goal is really just the name plus tidy ownership, **A** (or **B**) reaches the user's stated intent at materially lower risk and keeps the tested pure-core isolation without a major-version migration. This does **not** overturn the confirmed C decision — it surfaces the cheaper end-states the audit's evidence supports, per the repo rule to present alternatives before a large refactor.

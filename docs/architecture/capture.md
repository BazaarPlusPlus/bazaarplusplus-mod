# Combat Replay, Screenshots, Uploads, And Ghost Battles

Replay recording and playback, optional video capture, end-of-run screenshot capture, bundle sealing, the single upload feed, and ghost battle import.

Combat replay records local PvP battle replay payloads and lets HistoryPanel start playback when a local or downloaded ghost replay payload is available. Video recording is optional and supported on macOS and Windows through platform-native render plugins: Metal/VideoToolbox/AVFoundation on macOS, D3D11/Media Foundation on Windows. Availability is gated by the native plugin and output directory configuration (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayRecordingGate.cs`).

`tools/PeriodicEffectAttribution.Corpus/` is the opt-in offline evidence project for the Combat Impact periodic model; `tests/PeriodicEffectAttribution.Corpus/evidence/README.md` documents the retained corpus evidence, and `./run.sh test-corpus <path>` requires an explicit replay directory. Saved-replay playback state algebra lives in the pure `SavedReplayLifecycle` core: staged start commits, the 15-second exit-suppression latch shared by the continue/bootstrapped-exit/native-exit paths, the two-phase exit decision around the ended-publish, pending menu-return polling (a state parallel to start progress), and startup-interruption relay. `CombatReplayRuntime` is its translation layer — it executes publishes, portrait cleanup, and menu dispatch but holds no transition logic (`src/BazaarPlusPlus/Game/CombatReplay/SavedReplayLifecycle.cs`; behavior tests in `tests/CombatReplayPlaybackLogging.Tests/SavedReplayLifecycleTests.cs`; contract points in ADR-0011).

Saved-replay startup treats the native `ReplayState.SpawnCombatCards` task as the board-readiness boundary. Native state entry starts that task without awaiting it, so sampling active item setup or `BoardManager` flags alone can observe a false quiet frame before the first controller activates. The Harmony seam tracks both the complete board-spawn task and individual item setup tasks inside a scoped `ReplayPresentationTaskTracker`; startup waits until all tracked work completes and a render boundary passes without discovering new work, under the existing bounded failure rollback (`src/BazaarPlusPlus/Patches/Combat/CombatReplayItemPresentationReadinessPatch.cs`, `src/BazaarPlusPlus/Game/CombatReplay/Bootstrap/ReplayItemPresentationReadiness.cs`). Fixed delays and expected-controller counts are not substitutes for this native work boundary.

When recording starts, `CombatReplayVideoRecorder` creates a capture session, stores temp/final output paths, starts audio taps, suppresses selected BPP chrome, saves start metadata, and starts the capture coroutine (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoRecorder.cs`). Audio capture is additive: capture failure does not abort video recording. The recorder derives a WAV path, starts the platform capture tap if available, and logs/cleans up on failure (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoRecorder.cs`). On playback end, it closes the audio taps, retains only usable sample-bearing WAVs, freezes the finalization inputs into detached contexts, dispatches encoder drain/audio mux/metadata completion off the main thread, and clears the active state so a later replay cannot overwrite those inputs (`src/BazaarPlusPlus/Game/CombatReplay/Video/CombatReplayVideoRecorder.cs`, `src/BazaarPlusPlus/Game/CombatReplay/Audio/ReplayAudioTapStopper.cs`).

BPP UI chrome suppression is centralized in `Game/OverlayPanels`. Screenshot mode hides the CollectionPanel dock button and the combat status bar; replay recording mode hides only the dock button, intentionally leaving the combat status bar visible. There is no separate settings-dock suppression target (`src/BazaarPlusPlus/Game/OverlayPanels/BppUiChromeSuppression.cs`).

End-of-run capture is one run-scoped `EndOfRunCaptureWorkflow`: its core owns generation, summary readiness, automatic capture, the bounded pre-frame retry budget, reveal/frame/metadata deadlines, artifact validation, metadata persistence, late-artifact cleanup, Continue blocking, and the single terminal outcome (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCaptureWorkflowCore.cs`). Readiness requires native reveal start, a cleared screen transition, settled skills, and either 500 ms of structural card-pose stability after observed motion or the native `FaceUp` completion fallback; empty card boards retain their native settled path. The internal `EndOfRunCaptureDriver` is the Unity/native surface adapter for lifecycle signals, throttled screen discovery, card-hierarchy sampling, next-loop/end-of-frame capture scheduling, and BPP chrome suppression (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCaptureDriver.cs`). Continue stays blocked only until the settled frame's RGBA pixels have been copied out of Unity; PNG encoding, atomic file write, and metadata persistence then continue in the background without consuming or replaying the native click. Composition constructs the workflow and exposes its two-intent interface to patches before mounting that driver, so the Continue and raw reveal patches fail open during startup and teardown (`src/BazaarPlusPlus/BppComposition.cs`, `src/BazaarPlusPlus/BppComposition.cs`, `src/BazaarPlusPlus/Patches/EndOfRun/EndOfRunScreenshotPatch.cs`, `src/BazaarPlusPlus/Patches/EndOfRun/EndOfRunSummaryRevealPatch.cs`). A verified PNG is never deleted or recaptured when metadata persistence fails or times out; a late artifact from a capture canceled before frame acquisition is deleted (`src/BazaarPlusPlus/Game/Screenshots/EndOfRunCaptureWorkflowCore.cs`).

`BundleSealCoordinator` is the single background workflow owner of V5 input convergence, payload composition, screenshot JPEG budgeting, deterministic bundle construction, self-open verification, atomic publication, and crash reconciliation. Event-bus handlers only enqueue wakes. `BundleSealConvergence` owns the pure wait/degrade/terminal decision over a caller-supplied relative deadline; `BundleQueueStore` owns all seal-job/outbox SQL and transactions; the coordinator translates between them and retains codec/ImageSharp/file orchestration (`src/BazaarPlusPlus/Game/BundlePipeline/BundleSealConvergence.cs`, `src/BazaarPlusPlus.Storage/BundleQueue/BundleQueueStore.cs`, `src/BazaarPlusPlus/Game/BundlePipeline/BundleSealCoordinator.cs`). Stable bundle id/time are allocated before file creation, and startup recovery adopts a renamed file only when its durable allocation identity matches (`src/BazaarPlusPlus/Game/BundlePipeline/BundleSealCoordinator.cs`).

There is exactly one upload feed and one `BackgroundUploadPump`: each `BundleUploadFeed.Session` owns a `ModApiSession`, sends immutable `.bundle` files to `POST /bundles` with `Content-Length` and `Content-Digest`, maps typed endpoint dispositions, persists retry time through `BundleQueueStore`, and commits success before deleting through the narrow `IBundleOutboxFiles` port (`src/BazaarPlusPlus/Game/BundlePipeline/BundleUploadFeed.cs`, `src/BazaarPlusPlus/Game/BundlePipeline/BundleUploadFeed.cs`, `src/BazaarPlusPlus/Game/BundlePipeline/BundleOutboxFiles.cs`). Ghost discovery uses `GET /ghost-battles?limit=200`; replay download uses the same plugin-owned session, validates the bundle and run identities through `RunBundleV5Contract`, reconstructs only a complete target battle, saves it atomically, and persists `remote_available`, `local_ready`, `unavailable_payload`, or `expired` so permanent failures are not retried (`src/BazaarPlusPlus/Game/HistoryPanel/Ghost/`, `src/BazaarPlusPlus.ModApi/Bundle/RunBundleV5Contract.cs`). The exact wire and payload contracts are documented in `docs/contracts/run-payload-v5.md`; transport/result/persistence ownership is recorded in ADR-0012.

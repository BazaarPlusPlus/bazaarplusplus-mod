# Encounter Preview, Card Preview, And Tooltips

The Encounter Preview query boundary, the native card preview owning module, and the tooltip presentation surfaces. `GameInterop/Tooltips` holds two adapters that must not be merged.

`EncounterPreviewModule` is the single owner of event, encounter-step, and hero-level preview semantics. Its typed query interface accepts only stable template ids/current level plus native text already present at the patch boundary; the module reads the current static-data source, hero, inventory, one generation-matched day-tier result, and native keyword typography through `IEncounterPreviewGameRuntime` (`src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewModule.cs`, `src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewGameRuntime.cs`). It owns cache identity/read/write, plan compilation, generation publication, dynamic evaluation, localization, and final presentation. Event, encounter-step, and hero-level queries all resolve to the single `EventPreviewResult` record (`src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewModule.cs`). Beginning a source generation first removes the old snapshot; generation checks prevent a superseded load from publishing, while a successful compile remains published with degraded status if its cache write fails (`src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewModule.cs`, `src/BazaarPlusPlus/Game/EventPreview/EncounterPreviewPlanRegistry.cs`).

`EventPreviewStaticDataObserver` is only the Unity frame adapter that reports a newly ready source to the module (`src/BazaarPlusPlus/Game/EventPreview/EventPreviewStaticDataObserver.cs`). Tooltip patches receive the module through the `BppPatchFeatures` bundle and consume semantic results; they do not read plans, static-data maps, inventory, or CollectionPanel formatters (`src/BazaarPlusPlus/Patches/BppPatchFeatures.cs`, `src/BazaarPlusPlus/Patches/Tooltips/EncounterEventTooltipPatch.cs`, `src/BazaarPlusPlus/Patches/Tooltips/HeroLevelRewardsTooltipPatch.cs`). BazaarAgent receives the same event/step result through the passive `BazaarAgentGameBridge` facade, normalized to plain text before the host appends it to the native encounter description (`src/BazaarPlusPlus/Game/EventPreview/BazaarAgentEncounterPreview.cs`, `src/BazaarPlusPlus.BazaarAgentHost/BazaarAgentGameContextReader.cs`). `CardAbilityValueReader` centralizes the shared reflection seam over game-authored ability/aura action and attribute values; Event Preview and Collection keep their separate localization and typography policies (`src/BazaarPlusPlus/GameInterop/Cards/CardAbilityValueReader.cs`, `src/BazaarPlusPlus/Game/EventPreview/EventPreviewLocalization.cs`, `src/BazaarPlusPlus/Game/CollectionPanel/Data/CollectionLocalizationResolver.cs`). `GameDataDayTierResolver` is the shared GameInterop owner for Collection and Event Preview: it resolves the active manager reference, `GameModeId`, and run day into a normalized positive-finite distribution plus the highest usable Bronze-to-Diamond tier; it exposes typed unavailable states, caches successes only within one manager generation, retries transient readiness, and rejects an Event Preview query whose plan source is no longer the current manager (`src/BazaarPlusPlus/GameInterop/DayTiers/`).

`GameInterop/CardPreview` is the owning module for native card prefab selection, instantiation, setup/resize, reflection, hover state, tooltip replacement, pooling, and destruction. Production callers see only `INativeCardPreviewHost`, a per-owner `INativeCardPreviewScope`, and opaque `INativeCardPreviewSession` intent operations (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewContracts.cs`). Each scope has its own pool: closing rejects new acquisitions, cancels and waits outstanding setup, invalidates/destroys active sessions, then destroys idle objects; a session released after closing cannot re-enter the pool (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewHost.cs`, `src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewScopeLifetime.cs`).

Successful acquisition means the game template was resolved, a synthetic instance was built, the owner prepared the inactive prefab, and native setup plus resize completed before the session was delivered (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewFactory.cs`). The host also owns complete presentation visibility: the game's `CardPreviewBase.Show` covers only art/frame, so item gem groups remain concealed through setup and cancellation, are revealed only after a successful session `Show`, and are always concealed by `Hide` (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewPresentation.cs`, `src/BazaarPlusPlus/GameInterop/CardPreview/NativePreviewPresentationTransaction.cs`). Tooltip modifier refresh verifies that the visible primary tooltip belongs to the hovered session, writes replacement data, reapplies content to the existing native controller, and synchronously settles layout behind a temporary visibility gate; it does not replay native hide/show positioning and fades (`src/BazaarPlusPlus/GameInterop/CardPreview/NativeCardPreviewHost.cs`, `src/BazaarPlusPlus/GameInterop/Tooltips/NativeCardTooltipContentRefresher.cs`). Concrete pool/runtime/reflection/resource types are confined to this owning module by `NativeCardPreviewArchitectureTests`.

Enchant preview visibility is a three-state setting controlled by `PreviewVisibilityMode`: `Off`, `AutoOnPedestalChoice`, and `Always` (default `Always`). `ItemEnchantPreviewSettingsDockEntry.Create()` supplies its cycle order (`Off → AutoOnPedestalChoice → Always`), and `BppSettingsDockCatalog.ResolvePreviewVisibilityModeStatus` its status labels (`src/BazaarPlusPlus/Game/ItemEnchantPreview/ItemEnchantPreviewSettingsDockEntry.cs`). Enchant text is useful always but can be noisy or irrelevant, hence the automatic pedestal-relevance mode between the explicit off/always choices; upgrade preview is an on-demand comparison, so it deliberately has no visibility mode — only `Hold` (default) or `Toggle` activation for its shared key, persisted as `[Hotkeys] UpgradePreviewActivationMode` with no legacy boolean migration. `HotkeyActivationState` resets the latched toggle state when the activation mode or binding changes and processes at most one transition per frame (`src/BazaarPlusPlus/Game/Input/HotkeyActivationState.cs`).

`TooltipPreviewModePolicy` owns preview priority. Upgrade hotkey wins first, then enchant hotkey, then enchant `Always`, then enchant `AutoOnPedestalChoice` only when the current choice pedestal is an enchant pedestal (`src/BazaarPlusPlus/Game/Tooltips/TooltipPreviewModePolicy.cs`). A `TooltipModifierRefreshController` mountable re-resolves open preview tooltips when the Ctrl/Shift hold state changes; both ordinary game cards and hovered synthetic previews keep the existing native tooltip controller alive, replace its `CardTooltipData` through `ApplyPreviewTooltip`, and synchronously settle layout behind a temporary visibility gate instead of replaying native hide/show positioning and fades (`src/BazaarPlusPlus/Game/Tooltips/TooltipModifierRefreshController.cs`, `src/BazaarPlusPlus/Game/Tooltips/TooltipPreviewContentRefresh.cs`, `src/BazaarPlusPlus/GameInterop/Tooltips/NativeCardTooltipContentRefresher.cs`). The tooltip patch surface also covers encounter/event tooltips (gated by the `Game/EventPreview` settings toggle), quest reward previews and aggregate-item missing types (separate implementations sharing the default-off `QuestPreview/Enabled` gate), and hero level rewards (`src/BazaarPlusPlus/Patches/Tooltips/`). Disabling Quest Preview immediately restores tracked native quest text/layout and hides its pooled aggregate-item sections. Mod-appended text is rendered through the shared `BppTooltipSections` helper. Sections keep the cloned native donor typography and attach the game's own zh-CN fallback chain only when BPP-authored content contains CJK (`src/BazaarPlusPlus/Patches/Tooltips/BppTooltipSections.cs`, `src/BazaarPlusPlus/Patches/Tooltips/BppTooltipSections.cs`).

`GameInterop/Tooltips` holds two unrelated native-tooltip adapters that must not be merged. `NativeCardTooltipContentRefresher` replaces the `CardTooltipData` of an already-visible primary tooltip and settles its layout (`src/BazaarPlusPlus/GameInterop/Tooltips/NativeCardTooltipContentRefresher.cs`). `NativePairedTooltipHost` owns the separate "custom content inside the native auxiliary tooltip, pinned beside the native card tooltip" presentation: native state capture/restore, the `CanvasGroupGate` visibility gates, the cloned native background, the paired fade, side selection, and coordinate conversion (`src/BazaarPlusPlus/GameInterop/Tooltips/NativePairedTooltipHost.cs`). Composition creates one plugin-lifetime host; it is not `IDisposable`, and the releasable unit is the `NativePairedTooltipSession` a feature acquires from it (`src/BazaarPlusPlus/BppComposition.cs`). The host reports placement outcomes through `PlacementResult` and never logs: reason codes, their once-only latches, and native show/hide arbitration stay with the consuming feature, because that latch behavior decides how many records reach the log. The host also does not arbitrate the native auxiliary singleton — other code drives it directly (`src/BazaarPlusPlus/Game/CombatReplay/CurrentReplayRecordingButtonController.cs`), so a single active session serializes only this host's own usage. Purely geometric decisions are the unit-tested `NativePairedTooltipPlacementMath`; the shared `NativePairedTooltipMetrics.Epsilon` deliberately serves both as a geometry tolerance and as the CanvasGroup alpha interactivity threshold. Combat Impact is currently the only consumer, and it supplies its own trim strategy through `IPairedContentBudget` (`src/BazaarPlusPlus/Patches/PostCombatImpact/NativePostCombatImpactTooltipView.cs`). That view is a feature UI adapter rather than a Harmony patch, so by the layering rules it belongs under `Game/`; it stays in `Patches/` as recorded debt. The host's generality is "multiple features sharing this paired shape", not "any native tooltip host" — with one consumer, the wider claim is untested. `NativePairedTooltipArchitectureTests` ratchets the plumbing into this module.

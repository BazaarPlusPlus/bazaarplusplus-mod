# Make BazaarAgent its own BepInEx plugin that consumes BazaarPlusPlus

The BazaarAgent automation bridge becomes an **independent, second BepInEx plugin** (`BazaarPlusPlus.BazaarAgentHost.dll`, with its own `[BepInPlugin]` + `[BepInDependency(<BazaarPlusPlus GUID>)]`) that references `BazaarPlusPlus.dll` as a game-interop substrate and the pure transport core `BazaarPlusPlus.BazaarAgent.dll`. The assembly dependency is inverted: BazaarPlusPlus **no longer knows BazaarAgent exists**, exposing instead a narrow public game-interop facade that the host plugin consumes. The pure core stays `System` + `Newtonsoft.Json` only. This supersedes [ADR-0005](0005-autobazaar-isolated-transport-core.md), whose named reopen condition was exactly "AutoBazaar ever needs to become its own BepInEx plugin."

## Context

ADR-0005 isolated the automation bridge into a transport-only core behind host-owned ports, with the host adapters compiled *into* the main `BazaarPlusPlus.dll` under `#if BPP_BAZAARAGENT_HOST`. That already met the *encapsulation* goal — the mod carries no play policy and the core is a pure, independently-tested leaf. What it did **not** provide is independent *packaging*: the host could not ship as its own plugin/deliverable, because the composition root inside BazaarPlusPlus had to mount it, and the main plugin owned the per-frame `Update()` that drove the core's `Tick()`.

A read-only feasibility audit (`docs/audits/2026-06-05-autobazaar-dependency-inversion-feasibility.md`) established the decisive facts: the only compile edge is `BazaarPlusPlus → BazaarPlusPlus.BazaarAgent`; the only reverse references were two `#if`-gated lines in `BppComposition`; and the main plugin actively *drives* the core (it is not a passive library the way the game DLLs are). A clean inversion therefore cannot be a mere `ProjectReference` flip — it forces BazaarAgent to own its own plugin entry and Unity lifecycle. The user confirmed that an independently-packaged BepInEx plugin for the agent is a genuine requirement — the precise reopen condition ADR-0005 named.

The rename `AutoBazaar → BazaarAgent` rides with this work, split into two buckets: a code-only, behavior-neutral rename (WP-R, already landed) and a user-visible migration (on-disk path, `endpoint.json` removal, no runtime cfg) that ships with this inversion under a release note.

## Decision

1. **Two plugins.** `BazaarPlusPlus.dll` stays the main plugin (entry `Plugin.cs`, role unchanged) and merely *adds* a small public game-interop facade. A new assembly `BazaarPlusPlus.BazaarAgentHost.csproj` carries its own `[BepInPlugin]` + `[BepInDependency(<BazaarPlusPlus GUID>)]`, references `BazaarPlusPlus.dll` + the pure core + the game/Unity/BepInEx/Harmony DLLs, and self-mounts (its `BaseUnityPlugin` hosts `Awake()`/`Update()`/`OnDestroy()`). The `#if BPP_BAZAARAGENT_HOST` registration in `BppComposition` is deleted. BazaarPlusPlus no longer references the agent module — **no cycle**.
2. **Dedicated public facade — not blanket-public, not `InternalsVisibleTo`.** BazaarPlusPlus exposes only what the context reader consumes — verified as just `IEncounterStateProbe`'s two used methods plus the pure id/flag snapshot DTOs (`EncounterIdsSnapshot`, `EncounterTargetingSnapshot`) and `EncounterTypeResolver.Resolve` — plus a public replay-activity signal that replaces the WP-0 `Func<bool>`. The host obtains the facade through a **public static accessor that BazaarPlusPlus sets during its `Awake()`** — safe because the host declares `[BepInDependency]`, so BazaarPlusPlus.Awake runs first. Everything else stays `internal`.
3. **Pure core preserved.** `BazaarPlusPlus.BazaarAgent.dll` stays `System` + `Newtonsoft.Json` only, keeping the fast `net10.0` isolation tests in `tests/BazaarAgent.Tests`. All game/Unity/BepInEx/Harmony coupling lives in the new host assembly.
4. **CombatReplay coupling** is an event-bus / `Func<>` probe (WP-0), not a promotion of `CombatReplayRuntime` to public — it is one transient bool.
5. **No BazaarAgent runtime cfg.** Installing `BazaarPlusPlus.BazaarAgentHost.dll` enables the listener automatically at fixed `127.0.0.1:47900`; removing the dll disables it. The old `Enabled` and `HttpListenerPort` cfg keys are deleted, and the `/v1/context` `isEnabled` body field is removed under schema `2.0.0`. Ships with a release note; there is no first-party consumer to update (the installer, server, and site have no `[AutoBazaar]`/port awareness).
6. **`endpoint.json` is removed entirely.** It had no active code consumer anywhere in the `bpp/` workspace (it was written/deleted only by the HTTP server), the port is config-driven with a fixed default `47900` (nothing to discover), and the external `bazaarplusplus-agent` is a stdio JSONL server, not an HTTP-discovery client. Removing it drops `EndpointFilePath` from the pure-core `IBazaarAgentOptions` and eliminates the path-move risk class.
7. **On-disk decision-log path moves** `BazaarPlusPlus/AutoBazaar` → `BazaarPlusPlus/BazaarAgent`. After the `endpoint.json` removal this relocates only `decisions.jsonl` / `runs/<runId>/decisions.jsonl` (developer diagnostics, append-only) — no data migration is warranted; the new location is noted in the release note.
8. **Omittability becomes two independent top-level deliverables.** A default mod build ships only `BazaarPlusPlus.dll`; the host plugin is an on-demand build artifact. Because BazaarPlusPlus no longer references the agent module, it can no longer express omittability via a conditional `ProjectReference`; instead a default build must **actively scrub both** new artifacts (`BazaarPlusPlus.BazaarAgentHost.dll` and `BazaarPlusPlus.BazaarAgent.dll`) from `BepInEx/plugins` and both installer payload trees, even immediately after an on-demand host build. The chosen shape: the **host project owns the copy** of both dlls (`AfterTargets="Build"`), while **the main project keeps owning the delete** — its existing Debug `FilesToDelete` and Release `InstallerFilesToDelete` lists carry both host dll filenames *unconditionally* (the main build never produces them). BazaarPlusPlus naming two dll filenames in a delete list is not a code dependency (no `using`, no `ProjectReference`), so it does not reintroduce the cycle. This scrub is guarded by a new architecture/build test.
9. **Release version** is `4.1.0`; the intermediate `5.0.0` and `6.0.0` internal bumps were never published.

## Consequences

- The wire contract is unchanged: the v1 JSON field names (`stateName`, `availableActions`, `actionKind`, `cardInstanceId`, `targetSection`, `targetSockets`, `reason`) stay; the rename touched only C# type/identifier names, which are not on the wire.
- A new cross-plugin per-frame surface exists: the host plugin's `Update()` reads BazaarPlusPlus state. `[BepInDependency]` orders only `Awake`, not `Update`; the WP-0 CombatReplay cut removes the sharpest shared-mutable-singleton race.
- BazaarPlusPlus gains a small permanent public surface (the game-interop facade). This is the deliberate cost of independent packaging; it is narrower than blanket-public and avoids naming the agent module via `InternalsVisibleTo`.
- ADR-0005's transport-only-core and no-play-policy constraints survive unchanged; only the host-ownership/packaging model changes (host adapters move out of `BazaarPlusPlus.dll` into the new plugin assembly). The core's `System`+`Newtonsoft`-only constraint and the `tests/BazaarAgent.Tests` isolation ring are preserved.
- Reopen if the agent ever needs to drive BazaarPlusPlus features beyond the facade, or if a first-party HTTP-discovery client is ever built (which would revisit the `endpoint.json` removal).
